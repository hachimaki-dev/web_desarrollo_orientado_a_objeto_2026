Caso de negocio

Una tienda de videojuegos necesita un sistema de consola para gestionar su inventario de productos. La tienda vende dos tipos de productos: productos físicos (cajas, discos) y productos digitales (códigos de descarga). Ambos comparten datos generales como nombre, precio base y stock, pero se diferencian en sus atributos específicos y en la forma de calcular su precio final.

El sistema debe permitir registrar productos, listar el inventario, buscar productos por nombre, vender unidades y ver un resumen del inventario. Todas las entradas del usuario deben estar protegidas contra errores.

Antes de escribir código: leer y descomponer

El error más común es abrir el editor y empezar a escribir código inmediatamente. Antes de tocar el teclado, necesitas responder tres preguntas:

  1. ¿Qué entidades existen en este problema? — Lee el caso de negocio y subraya los sustantivos. Cada sustantivo relevante es un candidato a clase.
  2. ¿Qué datos tiene cada entidad? — Los datos de cada entidad serán sus atributos.
  3. ¿Qué acciones puede realizar cada entidad? — Las acciones serán sus métodos.

Analogía LEGO: Imagina que tienes una caja de LEGO con instrucciones. No empiezas armando al azar. Primero miras la imagen del modelo terminado (el caso de negocio), luego identificas las piezas que necesitas (las clases), y después sigues el orden de armado (primero la base, luego las paredes, al final el techo). Programar es lo mismo: primero entiendes, luego planificas, y al final escribes.

Identifica las entidades del caso

Del texto del caso de negocio, los sustantivos relevantes son:

  • Producto — concepto general, compartido por todos los tipos.
  • Producto físico — un tipo específico de producto.
  • Producto digital — otro tipo específico de producto.

Esas tres entidades son las tres clases que necesitas crear. Cada una será un archivo .java separado.

¿Por qué un archivo por clase? En Java, la convención es que cada clase pública vive en su propio archivo, y el nombre del archivo debe coincidir exactamente con el nombre de la clase. Si la clase se llama Producto, el archivo se llama Producto.java. Esto no es opcional — el compilador lo exige.

Identifica la relación entre las entidades

El caso dice: "Ambos comparten datos generales como nombre, precio base y stock, pero se diferencian en sus atributos específicos". Esto indica una relación de herencia:

  • Producto tiene los datos comunes (nombre, precioBase, stock).
  • ProductoFisico tiene todo lo de Producto más su dato propio (costoEnvio).
  • ProductoDigital tiene todo lo de Producto más sus datos propios (descuento, plataforma).

¿Por qué herencia y no copiar los atributos? Si copiaras nombre, precioBase y stock en cada clase, tendrías código duplicado. Si mañana necesitas agregar un cuarto atributo común (por ejemplo, categoria), tendrías que modificar tres archivos en vez de uno. La herencia resuelve esto: defines lo común una vez en el padre y las hijas lo reciben automáticamente.

Define el orden de construcción

Igual que en LEGO, hay un orden lógico. No puedes armar el techo antes que las paredes. En este caso:

  1. Pieza 1: Producto.java — la base. Las hijas dependen de ella.
  2. Pieza 2: ProductoFisico.java — primera hija. Necesita que Producto ya exista.
  3. Pieza 3: ProductoDigital.java — segunda hija. También necesita que Producto ya exista.
  4. Pieza 4: Main.java — el programa principal. Necesita que todas las clases existan para poder usarlas.

Error frecuente: Empezar por Main.java. Si lo haces, vas a intentar crear objetos de clases que todavía no existen, y el compilador te va a devolver errores. Esto genera frustración y pérdida de tiempo. Empieza por las piezas base.

Pieza 1 — La clase Producto

Esta es la base de todo. Producto define qué datos y comportamientos comparten todos los productos, sin importar si son físicos o digitales.

1A — ¿Por qué la clase es abstracta?

El caso dice que el precio final se calcula diferente para cada tipo: el físico suma costo de envío y el digital aplica descuento. Entonces la clase Producto sabe que el método calcularPrecioFinal() debe existir, pero no sabe cómo calcularlo, porque depende del tipo concreto.

Cuando una clase tiene al menos un método que dice "esto debe existir, pero cada hijo define cómo", esa clase es abstracta.

Analogía: Un formulario de impuestos tiene un campo "Monto a pagar", pero el cálculo depende de si eres persona natural o empresa. El formulario define que el campo existe; cada tipo de contribuyente define cómo se llena. La clase abstracta es el formulario. Las clases hijas son los tipos de contribuyente.

En Java, declarar una clase abstracta se hace así:

public abstract class Producto {
    // contenido
}

¿Qué implica abstract en la práctica? Que no puedes escribir new Producto(...). No puedes crear un "producto genérico" — siempre tiene que ser un ProductoFisico o un ProductoDigital. Esto tiene sentido: en la tienda real, nunca vendes "un producto" a secas. Siempre es un juego físico o un código digital.

1B — Los atributos y por qué son privados

Del diagrama UML, Producto tiene tres atributos: nombre, precioBase y stock. Los tres están marcados con - (guion), que en UML significa privado.

¿Por qué privados y no públicos? Si el atributo stock fuera público, cualquier parte del código podría escribir producto.stock = -50 y dejar el inventario en un estado imposible. Al hacerlo privado, obligamos a que el acceso pase por métodos (getters/setters) donde podríamos agregar validación. Esto es encapsulamiento: controlar quién puede ver y modificar los datos internos de un objeto.

Declarar atributos privados en Java se ve así:

private String nombre;
private int precioBase;
private int stock;

Estas tres líneas van dentro de la clase Producto, antes del constructor. Son las "propiedades" que todo producto tiene.

¿Por qué int y no double para los precios? El enunciado dice que los precios son enteros (pesos chilenos sin decimales). Usar int simplifica los cálculos y evita errores de precisión decimal. Si el caso pidiera centavos, usaríamos double o long.

1C — El constructor: cómo se crea un objeto

Un constructor es un método especial que se ejecuta cuando creas un objeto con new. Su trabajo es recibir los datos iniciales y guardarlos en los atributos.

El constructor de Producto necesita recibir los tres datos comunes: nombre, precioBase y stock. Dentro del constructor, usas this. para distinguir entre el atributo de la clase y el parámetro que recibiste.

ElementoQué esEjemplo
this.nombre El atributo de la clase (el que declaraste arriba con private) El "cajón" donde se guarda el dato permanentemente
nombre (sin this) El parámetro que llegó al constructor El "sobre" que alguien te entregó con un valor

La línea this.nombre = nombre; significa: "toma el valor que me dieron en el parámetro y guárdalo en el atributo de esta instancia".

Error frecuente: Olvidar this. y escribir nombre = nombre;. Esto no hace nada útil — le asigna el parámetro a sí mismo, y el atributo queda en null o 0. El compilador no te avisa de este error. El programa compila, pero los datos no se guardan.

1D — Getters y setters: la puerta controlada a los datos

Como los atributos son privados, otras clases no pueden leerlos directamente. Los getters son métodos públicos que devuelven el valor de un atributo. Los setters son métodos públicos que permiten modificarlo.

Para Producto, necesitas:

  • getNombre() — retorna String. Solo lectura.
  • getPrecioBase() — retorna int. Solo lectura.
  • getStock() — retorna int. Solo lectura.
  • setStock(int stock) — modifica el stock. Se necesita porque al vender un producto, Main debe poder actualizar el stock.

¿Por qué solo setter para stock y no para nombre o precio? Porque en este caso de negocio, una vez que registras un producto, su nombre y precio no cambian. El único dato que se modifica durante la ejecución es el stock (cuando vendes unidades). Si el caso pidiera "editar producto", necesitarías setters para los otros atributos también. Cada setter que creas es una decisión de diseño: ¿quién necesita modificar este dato y cuándo?

Un getter sigue siempre el mismo patrón:

public int getPrecioBase() {
    return precioBase;
}

Retorna el valor del atributo privado. Nada más. Un setter recibe un valor y lo asigna:

public void setStock(int stock) {
    this.stock = stock;
}

1E — El método abstracto: una promesa a las hijas

calcularPrecioFinal() es un método abstracto. Esto significa que Producto lo declara pero no lo implementa. No tiene llaves {} ni cuerpo. Solo tiene la firma y un punto y coma:

public abstract int calcularPrecioFinal();

¿Qué logra esto? Dos cosas. Primero, obliga a que toda clase que herede de Producto implemente este método — si no lo hace, el compilador da error. Segundo, permite que en el Main puedas llamar a producto.calcularPrecioFinal() sin saber si es físico o digital, y Java ejecutará la versión correcta según el tipo real del objeto. Esto es polimorfismo.

1F — mostrarInfo(): un método concreto que las hijas pueden sobrescribir

A diferencia de calcularPrecioFinal(), mostrarInfo() sí tiene implementación en Producto. Retorna un String con la información base: nombre, precio base, precio final y stock.

¿Por qué retorna String en vez de usar System.out.println directamente? Si el método imprime directo, está acoplado a la consola. Si mañana quieres mostrar esos datos en una interfaz gráfica o guardarlos en un archivo, tendrías que reescribirlo. Al retornar un String, quien llame al método decide qué hacer con el texto: imprimirlo, guardarlo, o cualquier otra cosa. Es un principio de diseño: separar la lógica de la presentación.

Dentro de mostrarInfo() puedes llamar a calcularPrecioFinal() aunque sea abstracto. ¿Por qué? Porque este método nunca se ejecutará en un Producto directamente (es abstracto, no puedes crear instancias). Se ejecutará en un ProductoFisico o ProductoDigital, que sí tienen implementación del método. Java resuelve la llamada en tiempo de ejecución.

Un ejemplo de cómo armar el String:

return nombre + " | Base: $" + precioBase + " | Final: $" + calcularPrecioFinal() + " | Stock: " + stock;

Pieza 2 — La clase ProductoFisico

Esta clase es la primera "hija" de Producto. Hereda todo lo que tiene el padre y agrega lo propio de un producto físico.

2A — Declarar la herencia con extends

En Java, para decir que una clase hereda de otra, usas la palabra extends:

public class ProductoFisico extends Producto {
    // contenido
}

Con esta línea, ProductoFisico ya tiene los tres atributos del padre (nombre, precioBase, stock), sus getters, su setter, y su mostrarInfo(). No necesitas volver a escribirlos.

¿Por qué extends y no copiar el código? Porque la herencia crea una relación de tipo: un ProductoFisico es un Producto. Esto permite que un ArrayList<Producto> acepte objetos de tipo ProductoFisico. Si solo copiaras el código, ProductoFisico no sería compatible con Producto — serían dos clases independientes y no podrías mezclarlos en la misma lista.

2B — El atributo propio

ProductoFisico agrega un atributo que el padre no tiene: costoEnvio. Este dato es privado (igual que los del padre) y es exclusivo de esta clase.

private int costoEnvio;

¿Por qué no agregar costoEnvio en Producto? Porque un producto digital no tiene costo de envío. Si lo pusieras en el padre, ProductoDigital heredaría un dato que no le corresponde. Cada clase debe tener solo los atributos que le son relevantes.

2C — El constructor y super()

ProductoFisico necesita un constructor que reciba 4 datos: los 3 del padre (nombre, precioBase, stock) más el propio (costoEnvio). Pero los 3 datos del padre los debe inicializar el constructor del padre. Para eso usas super():

public ProductoFisico(String nombre, int precioBase, int stock, int costoEnvio) {
    super(nombre, precioBase, stock);
    this.costoEnvio = costoEnvio;
}

¿Qué hace super(nombre, precioBase, stock)? Llama al constructor de la clase padre (Producto) y le pasa los tres valores. El padre se encarga de guardarlos en sus atributos con this.nombre = nombre, etc. La hija no debería tocar los atributos privados del padre directamente — no puede, porque son privados.

Error frecuente: Intentar escribir this.nombre = nombre; dentro del constructor de ProductoFisico. Esto falla porque nombre es private en Producto, y private significa que solo la propia clase puede acceder. La hija usa super() para delegar esa responsabilidad al padre.

Error frecuente: super() debe ser la primera línea del constructor de la hija. Si intentas poner this.costoEnvio = costoEnvio; antes de super(), el compilador da error. Java exige que el padre se inicialice primero.

2D — Implementar calcularPrecioFinal()

Como Producto declaró calcularPrecioFinal() como abstracto, ProductoFisico está obligada a implementarlo. Si no lo hace, el compilador da error.

Para un producto físico, el precio final es precioBase + costoEnvio. Pero precioBase es privado en el padre. ¿Cómo accedes? Usando el getter: getPrecioBase().

@Override
public int calcularPrecioFinal() {
    return getPrecioBase() + costoEnvio;
}

¿Qué es @Override? Es una anotación que le dice al compilador: "estoy sobrescribiendo un método del padre". No es obligatorio escribirla, pero es una buena práctica. Si te equivocas en el nombre del método (por ejemplo, escribes calcularPrecioFianl), sin @Override Java cree que estás creando un método nuevo y no te avisa. Con @Override, el compilador verifica que realmente exista un método con ese nombre en el padre, y si no lo encuentra, te da error. Es una red de seguridad.

¿Por qué getPrecioBase() y no precioBase? Porque precioBase es private en Producto. La clase hija no puede acceder a atributos privados del padre. Solo puede acceder a lo que sea public o protected. Los getters son públicos, así que por ahí se accede. Es encapsulamiento funcionando.

2E — Sobrescribir mostrarInfo()

Producto ya tiene un mostrarInfo() funcional. Pero para ProductoFisico queremos agregar información adicional: el tipo ("Físico") y el costo de envío.

Sobrescribes el método con @Override y construyes un String que incluya toda la información relevante. Puedes armar el texto desde cero o reutilizar parte de lo que ya tiene el padre.

¿Qué formato usar? Mira el ejemplo de ejecución en la pestaña "Caso de negocio". Los productos se muestran como: Físico | The Legend of Zelda | Base: $49990 | Envío: $3990 | Final: $53980 | Stock: 10. Tu mostrarInfo() debe armar un String con ese formato o uno similar.

Pieza 4 — Main.java: la estructura base

Main.java es donde vive el método main — el punto de entrada del programa. También es donde declararás los métodos que implementan cada opción del menú.

4A — Las herramientas que necesitas al inicio

Antes de la declaración de la clase, necesitas importar las herramientas que vas a usar:

  • java.util.ArrayList — la colección para guardar productos.
  • java.util.Scanner — para leer datos del teclado.
import java.util.ArrayList;
import java.util.Scanner;

¿Por qué importar? En Java, las clases que no son del paquete base (java.lang) necesitan ser importadas explícitamente. String, int y System no necesitan import porque son parte de java.lang. Pero ArrayList y Scanner están en java.util, así que hay que importarlos. Si no los importas, el compilador no sabe qué son y da error.

4B — Las variables del método main

Dentro del main, necesitas crear dos objetos que usarás durante toda la ejecución:

  1. El Scanner: para leer entradas del teclado.
  2. El ArrayList: la colección que almacena todos los productos.
  3. Una variable boolean: para controlar cuándo termina el menú.
Scanner scanner = new Scanner(System.in);
ArrayList<Producto> inventario = new ArrayList<>();
boolean ejecutando = true;

¿Por qué ArrayList<Producto> y no ArrayList<ProductoFisico>? Porque necesitas guardar ambos tipos de productos en la misma lista. Si declaras ArrayList<ProductoFisico>, solo podrías agregar productos físicos. Al usar el tipo padre Producto, la lista acepta cualquier objeto que sea un Producto — ya sea físico o digital. Esto es polimorfismo aplicado a colecciones.

¿Por qué estas variables se declaran dentro de main y no a nivel de clase? Porque solo se usan durante la ejecución del programa. No son datos permanentes de una entidad — son herramientas temporales del flujo de ejecución. En POO, los atributos de clase representan el estado de una entidad. El Scanner y la variable ejecutando no son "estado" de nada; son herramientas del programa.

4C — El bucle del menú

El menú se repite mientras ejecutando sea true. En cada iteración, imprime las opciones, lee lo que escribe el usuario, y usa un switch para decidir qué hacer.

¿Por qué while y no for? Un for se usa cuando sabes cuántas veces va a iterar (por ejemplo, recorrer una lista de 10 elementos). Un while se usa cuando la condición de parada depende de algo que cambia durante la ejecución (en este caso, que el usuario elija "Salir"). No sabes de antemano cuántas veces el usuario va a usar el menú.

¿Por qué leer la opción como String y no como int? Si usas scanner.nextInt() y el usuario escribe "abc", el programa lanza una excepción. Si lees como String con scanner.nextLine(), nunca falla — puedes comparar el texto con los casos del switch. Es más seguro y más simple para un menú.

Estructura del menú:

while (ejecutando) {
    System.out.println("\n=== TIENDA DE VIDEOJUEGOS ===");
    System.out.println("1. Registrar producto");
    // ... las demás opciones ...
    System.out.print("Seleccione una opción: ");
    String opcion = scanner.nextLine().trim();

    switch (opcion) {
        case "1":
            // llamar al método correspondiente
            break;
        // ... los demás casos ...
        case "6":
            ejecutando = false;
            break;
        default:
            // opción no válida
            break;
    }
}

¿Por qué cada opción llama a un método separado? Si pones toda la lógica dentro del switch, el main se convierte en un bloque de cientos de líneas imposible de leer. Al separar cada funcionalidad en un método, el main se lee como un índice: "caso 1 → registrar, caso 2 → listar, caso 3 → buscar...". Además, si un método tiene un bug, sabes exactamente dónde buscarlo. Esto es modularización.

4D — ¿Por qué los métodos son static?

Todos los métodos auxiliares en Main (registrar, listar, buscar, vender, resumen) deben ser static.

Razón técnica: El método main es static. Un método estático solo puede llamar a otros métodos estáticos de la misma clase. Si tus métodos auxiliares no son static, el compilador da error al intentar llamarlos desde main. Esto se debe a que un método estático no tiene una instancia (this) asociada — pertenece a la clase, no a un objeto.

Cada método auxiliar recibe como parámetro lo que necesita para trabajar. Típicamente el Scanner (para leer datos) y el ArrayList (para acceder al inventario).

¿Por qué pasar el ArrayList como parámetro y no declararlo a nivel de clase? Ambas opciones funcionan. Declararlo a nivel de clase (como static ArrayList<Producto> inventario) es más simple. Pasarlo como parámetro es más explícito — cada método declara qué datos necesita. Para esta evaluación, ambas opciones son válidas. Lo importante es que lo uses de forma consistente.

5B — Leer números del teclado con protección

Los datos como precio, stock y descuento son numéricos. El usuario escribe texto en la consola, y tú necesitas convertirlo a int. Esa conversión puede fallar si el usuario escribe letras.

System.out.print("Precio base: ");
int precioBase = Integer.parseInt(scanner.nextLine());

Si el usuario escribe "abc", Integer.parseInt lanza una NumberFormatException y el programa se detiene. Para evitar eso, envuelves la conversión en un try-catch:

try {
    System.out.print("Precio base: ");
    int precioBase = Integer.parseInt(scanner.nextLine());
    // ... continuar con el registro ...
} catch (NumberFormatException e) {
    System.out.println("Error: debe ingresar un número válido.");
}

¿Dónde poner el try-catch? Puedes envolver todo el proceso de registro en un solo try-catch grande. Si cualquier dato numérico falla, el catch captura el error, muestra el mensaje y el método termina. El flujo vuelve al menú principal automáticamente porque el método retorna.

5C — La sobrecarga de métodos

El caso pide implementar al menos un método sobrecargado. La sobrecarga es crear dos o más métodos con el mismo nombre pero diferentes parámetros. Java los distingue por la cantidad y tipo de parámetros, no por el nombre.

// Versión 1: solo mensaje
private static void mostrarMensaje(String mensaje) {
    System.out.println(mensaje);
}

// Versión 2: mensaje con tipo
private static void mostrarMensaje(String mensaje, String tipo) {
    System.out.println("[" + tipo + "] " + mensaje);
}

Cuando escribas mostrarMensaje("Producto registrado"), Java ejecuta la versión 1. Cuando escribas mostrarMensaje("Producto registrado", "OK"), ejecuta la versión 2. Java decide cuál usar según los argumentos que le pasaste.

¿Cuál es la diferencia entre sobrecarga y sobrescritura? La sobrecarga (overload) ocurre en la misma clase: mismo nombre, diferentes parámetros. La sobrescritura (override) ocurre entre padre e hija: mismo nombre, mismos parámetros, diferente implementación. mostrarMensaje con 1 y 2 parámetros es sobrecarga. calcularPrecioFinal() en Producto y ProductoFisico es sobrescritura.

Usa tus métodos sobrecargados en diferentes partes del código: al confirmar un registro, al mostrar un error, al dar información. Así demuestras que entiendes el concepto.

6A — Listar: donde el polimorfismo se hace visible

Este método recorre el ArrayList e imprime cada producto. Lo notable es que usas un solo bucle y un solo método (mostrarInfo()), pero cada producto se muestra con su formato propio.

¿Por qué funciona esto sin preguntar si es físico o digital? Porque mostrarInfo() está sobrescrito en cada clase hija. Cuando p es realmente un ProductoFisico, Java ejecuta la versión de ProductoFisico. Cuando es un ProductoDigital, ejecuta la versión de ProductoDigital. Tú no necesitas hacer ningún if ni instanceof. Esto es polimorfismo: la decisión de qué método ejecutar la toma Java en tiempo de ejecución, según el tipo real del objeto.

Error frecuente: Olvidar verificar si la lista está vacía antes de recorrerla. Si la lista está vacía, el bucle no ejecuta ninguna iteración, pero el usuario no ve nada y cree que el programa falló. Agrega un if (inventario.isEmpty()) al inicio del método para mostrar un mensaje claro.

6B — Buscar: recorrer con condición

La búsqueda pide un texto al usuario y recorre la lista comparando. Para buscar sin distinguir mayúsculas/minúsculas y de forma parcial:

// Convertir ambos a minúsculas para comparar
if (p.getNombre().toLowerCase().contains(textoBusqueda.toLowerCase())) {
    // mostrar este producto
}

¿Por qué toLowerCase() en ambos lados? Porque "Zelda".contains("zelda") es false — Java distingue mayúsculas de minúsculas por defecto. Al convertir ambos a minúsculas, "zelda".contains("zelda") es true. Es una técnica estándar para búsqueda insensible a mayúsculas.

Lleva un contador o una variable boolean para saber si encontraste resultados. Si al terminar el bucle no encontraste nada, muestra un mensaje.

📄 Producto.java Clase Abstracta R2 · IL 1.3 · IL 1.4

Superclase abstracta base. Encapsula atributos comunes, define el método abstracto calcularPrecioFinal() e implementa mostrarInfo().

/**
 * CLASE ABSTRACTA: Producto
 * 
 * Cumple con R2 (IL 1.3, IL 1.4).
 * Representa la abstracción base de cualquier artículo en la tienda.
 * Es abstracta porque no existen productos "genéricos": todo producto
 * comercializable es o Físico o Digital.
 */
public abstract class Producto {

    // --- Atributos privados (Principio de Encapsulamiento) ---
    // Ninguna clase externa ni subclase puede modificarlos directamente.
    private String nombre;
    private int precioBase;
    private int stock;

    /**
     * Constructor base. Inicializa el estado común a todo producto.
     * Es invocado por las subclases mediante super(nombre, precioBase, stock).
     */
    public Producto(String nombre, int precioBase, int stock) {
        this.nombre = nombre;
        this.precioBase = precioBase;
        this.stock = stock;
    }

    // --- Getters (lectura pública y controlada) ---

    public String getNombre() {
        return this.nombre;
    }

    public int getPrecioBase() {
        return this.precioBase;
    }

    public int getStock() {
        return this.stock;
    }

    // --- Setter para stock ---
    // El único atributo mutable: se actualiza cuando se concretan ventas.
    public void setStock(int stock) {
        this.stock = stock;
    }

    /**
     * MÉTODO ABSTRACTO: calcularPrecioFinal()
     * 
     * Define el contrato polimórfico. No posee cuerpo en esta clase porque
     * cada categoría calcula su precio con fórmulas distintas:
     * - Físico: suma costo de envío.
     * - Digital: aplica porcentaje de descuento.
     * 
     * Toda subclase no abstracta está OBLIGADA a proveer una implementación.
     */
    public abstract int calcularPrecioFinal();

    /**
     * MÉTODO CONCRETO: mostrarInfo()
     * 
     * Retorna un String con la información base del producto.
     * Las subclases pueden sobrescribirlo (@Override) para enriquecer el texto.
     * Invoque a calcularPrecioFinal(), resolviéndose polimórficamente en tiempo de ejecución.
     */
    public String mostrarInfo() {
        return "Producto: " + this.nombre +
               " | Base: $" + this.precioBase +
               " | Final: $" + calcularPrecioFinal() +
               " | Stock: " + this.stock;
    }
}

/**

 * Cumple con R4 (IL 1.3, IL 1.4).
 * Hereda de Producto y añade características de distribución digital:
 * - Plataforma (Steam, PS Store, Nintendo eShop, Xbox, etc.).
 * - Descuento promocional en porcentaje entero (0 al 100%).
 * - Su precio final descuenta el monto de descuento del precio base.
 */
public class ProductoDigital extends Producto {

    // Atributos exclusivos de la versión digital
    private int descuento;       // Porcentaje de descuento (ej: 15 para 15%)
    private String plataforma;   // Plataforma de activación o descarga

    /**
     * Constructor de ProductoDigital.
     * Recibe 5 parámetros: 3 del padre + 2 propios.
     */
    public ProductoDigital(String nombre, int precioBase, int stock, int descuento, String plataforma) {
        super(nombre, precioBase, stock);
        this.descuento = descuento;
        this.plataforma = plataforma;
    }

    // Getters propios
    public int getDescuento() {
        return this.descuento;
    }

    public String getPlataforma() {
        return this.plataforma;
    }

    /**
     * Sobrescritura (@Override) de calcularPrecioFinal().
     * Regla de negocio: Precio Base - (Precio Base * descuento / 100).

    @Override

    @Override

               " | Final: $" + calcularPrecioFinal() +
               " | Stock: " + getStock();
    }

                return;

            System.out.println("Unidades vendidas: " + cantidad);

            System.out.println("Stock remanente: " + productoSeleccionado.getStock() + " unidades");
